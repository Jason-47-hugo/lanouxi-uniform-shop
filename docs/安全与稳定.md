# 安全与稳定：这套小程序靠不靠得住

先分清楚两个东西，不然后面全是空话。

- **现在这个演示版**：页面和数据都在本机（微信开发者工具的 storage / 网页的 localStorage），没有服务器、没有账号体系。它是用来看界面、走流程的，**不能直接上线接真订单**。
- **上线版**：小程序前端 + 云开发（云数据库、云函数、云存储）。下面所有结论都按上线版来说。

---

## 1. 100 人同时在线会不会崩

**前端不会崩。** 小程序页面本身是静态的，打开一百次就是一百个互不相干的客户端，压力不在前端。

**压力在数据和图片。**

- 商品图：放云存储 + CDN，图片不经过你的服务器，几个人看和一百个人看没区别。
- 订单/积分：每次下单是一次数据库写入 + 一次云函数调用。云开发是按量伸缩的，几十个并发对它来说很轻。
- 真实峰值：一家校服店，开学前一周的晚上 8–10 点最忙。按 100 人同时浏览、其中 5–10 人同时下单估算，云开发的免费额度基本够用，超了也是几块钱的量级。

**要做的事：**

1. 列表页一次只拉 20 条，不要一次查全表。
2. 商品和学校名单做本地缓存（`wx.setStorageSync` + 版本号），少打数据库。
3. 下单按钮加防重复（点一次就置灰 + 订单号幂等），这是最容易出问题的地方，比并发本身更常见。
4. 上线前用微信开发者工具的「真机调试 + 多设备」跑一遍，不必做专业压测；真要有 100 人同时下单的那天，说明生意已经值得请人写后端了。

## 2. 别人能不能用 AI 改我的小程序

**拿不到源码，但前端代码不是秘密。**

- 小程序代码包在微信服务器上，别人没有你的 AppID 和管理员权限，改不了、也发不了版。
- 但小程序包可以被反编译（和网页 JS 一样）。所以：**价格、积分、订单状态这些关键判断不要只写在前端**，要放在云函数里。前端只负责显示。
- 真正的风险不是 AI，是**权限**：
  - AppID 的管理员只加你自己和你妈；
  - 「开发者」权限不要给不认识的代做；
  - 店长端不用口令，改成微信 openid 白名单（只有你妈的微信号能进）；
  - 开启微信的「登录保护 / 操作日志」，谁改了代码、谁发了版都有记录。

## 3. 钱会不会流出去

**这套方案里，平台从头到尾不碰钱。**

- 顾客扫的是你妈的收款码，钱直接进她的微信/银行卡，小程序只负责记录「谁下了哪一单、转了多少」。
- 所以不存在「平台跑路」「资金池」的问题；风险换成了另一种：**有人假装转账**。对策是店长在后台看到「待确认」后，去微信账单里核对金额和订单尾号，再点「确认收款」。现在店长台就是这个流程。
- 如果以后要做「自动到账」（顾客点一下直接付款），就必须申请微信支付商户号，钱进对公或个体户账户，T+1 结算，平台仍然不碰钱。这一步不影响现在上线。

## 4. 积分会不会凭空多出来

演示版里积分存在本机，改一改 storage 就能变——**上线版不能这样**。

上线后的规矩：

1. 积分只存在云数据库的 `users` 表，客户端只能读自己的。
2. 所有加减分都走云函数：下单扣分、确认收货返分、取消退回，云函数里重新算一遍金额，**不相信前端传上来的积分和价格**。
3. 每笔积分变动写一条 `points_logs`（谁、哪单、加减多少、时间），可对账、可回滚。
4. 幂等：一个订单只能返一次积分；云函数用订单号做唯一键，重复调用直接返回上次结果。
5. 上限：单笔抵扣不超过 5%，返分按实付金额向下取整，规则写死在云函数里。

这样即使有人改了手机本地数据，也只是他自己看到假的，服务器不受影响。

## 5. 数据会不会被改

- 数据库权限设成「仅创建者可读，写操作只允许云函数」。客户端拿不到写权限，想改也改不了。
- 云函数里校验：金额由服务端按商品单价重算，不信任前端传的 `amount`。
- 每天自动备份一次数据库（云开发支持定时触发器 + 导出 JSON 到云存储），保留 30 天。
- 店长端的每个操作（确认收款、发货、上下架）都写操作日志，出问题能查是谁点的。
- 真要防到「黑客级」，那是另一个预算的事；对一家校服店，上面五条已经能挡住 99% 的意外和恶意。

---

## 上线要补的东西（按顺序）

1. 注册小程序、拿 AppID（个人主体即可，不需要商户号）。
2. 开通云开发，建 4 张表：`products`、`orders`、`users`、`points_logs`。
3. 把 `utils/store.js` 里的本地逻辑拆成云函数：`createOrder`、`confirmPayment`、`ship`、`confirmReceipt`、`cancelOrder`、`checkIn`。
4. 图片换实拍图，传云存储；收款码换成你妈的真实收款码。
5. 店长入口改 openid 白名单，删掉口令 2468。
6. 真机走一单：下单 → 转账 → 店长确认 → 发货 → 收货 → 积分到账。

## 一句话总结

- 现在：能看、能点、能演示，数据在本机，**别收真钱**。
- 上线：云开发 + 云函数做权威，前端只显示；钱走你妈的码，平台不碰；积分和订单都在服务端算。
- 100 人同时用不是问题；真正要防的是「假装转账」和「前端改价」，这两条上面都给了做法。
