## a) 项目背景与动机

**一句话**：把妈妈经营的校服店搬到微信里，让家长不用在开学季反复私聊问"有没有货、多少钱、穿多大"，也让店长一个人能用手机接单、收款、发货。

- **现实场景**：家里经营校服生意（珠海本地多所中小学的校服款式），目前主要靠线下门店 + 微信私聊。开学前后家长集中询问款式、价格、尺码、库存，重复沟通成本高；店里忙的时候消息容易漏回。
- **为什么选这个题**：真实、可验证、用户就在身边（妈妈是店长，第一批家长用户可触达），而且能在课程周期内做出完整闭环：逛 → 选尺码 → 下单 → 付款 → 店长发货 → 确认收货 → 售后。
- **目标用户**：
  - 主用户：珠海本地中小学家长（30–45 岁），在微信里完成全部操作，耐心有限，最关心"是不是我校服、多少钱、多久到、尺码对不对"。
  - 次用户：店长（妈妈），需要极简的订单列表：谁下的、付没付、发什么快递、单号多少、要退哪件。
- **核心功能（MVP 范围）**：
  1. 校服商品展示：按学校 / 学段 / 品类筛选，商品详情含面料、尺码表、换码说明。
  2. 下单：购物车、快递或到店自提、收货信息、订单备注。
  3. 付款：调用微信支付（正式版接商户号），钱直接进店长绑定的银行卡，不经手第三方。
  4. 积分机制：积分可抵现（每单最多抵总额 5%），确认收货后按实付金额返积分；累计消费满 ¥1200 成为会员，全场 96 折。
  5. 退货：7 天无理由，店长在后台逐件勾选退货；退款按实付比例算，抵扣掉的积分按比例退回，已返购物积分按留下的金额重算。
  6. 店长端：订单列表与筛选、发货填单号、处理退货、商品改价改图改库存。
- **不做什么（本期）**：不做多店加盟、不做复杂售后仲裁、不做直播/拼团、不做签到。

## d) 遇到的问题与解决

> 记录真实发生的问题，写清"为什么"和"怎么验证解决"。

1. **支付的合规前提被误解了一轮**：最初以为个人主体永远开不了微信支付，就设计了收款码 + 人工确认。
   - 转折：店家明确要求"微信付款、绑定银行卡"，方案推翻。
   - 解决：订单状态机删掉 `pending_confirm`，改成 `pending_pay → paid`，付款成功由支付回调写状态；演示版用一个"模拟支付"按钮走同一条状态路径，正式版换成 `wx.requestPayment` + 云函数回调即可。
   - 教训：把"暂时做不到"写进设计的代价，比把"能不能做到"问清楚更大。
2. **店长身份识别**：不能让任意用户进入店长端改订单。
   - 解决（演示版）：店长入口 + 4 位口令（默认 2468），仅用于本地演示；正式版改为云开发 openid 白名单。
3. **没有真实商品图和商品数据**：不能直接搬样板小程序的图片（版权 + 不是自家货）。
   - 解决：先做一套统一的矢量插画占位（同色系、可整体替换）；店家确认"实物图片店主自己维护"后，把商品名称/价格/库存/图片做成店长台可编辑（`store.updateProduct`），拿到实拍图后店长自己拍自己换，不需要改代码。
4. **家长不会选尺码**：校服退换麻烦，尺码错一次就是一次售后。
   - 解决（v0.3 起）：详情页内置"身高/体重 → 推荐尺码"的对照表和宽松建议；下单页再次提示"拿不准选大一号"。
   - 升级（v0.6）：把对照表改成可点的小表单——填身高体重，「算一下」直接给出码位和一句理由，「就用它」就选中这个码。
     规则写成一个纯函数 `miniprogram/utils/size.js`：先按身高落档，再按体重浮动一档，BMI 过高/过低（>26 / <16）再浮动一档，最后夹进这件商品真实的尺码表，所以不会推荐不存在的码；均码商品直接返回该码。
   - 验证：`preview/flow-test.js` 第 11 节 10 条断言（各类商品的推荐结果必须落在自己的尺码表里），另加 `preview/itest-size.html` 在真实网页版里点一遍（13 条）。
5. **作业要求里的"访问信息"**：小程序不能像网页一样甩链接。
   - 解决：提交时给「小程序名称 + 体验版二维码 + 3 步打开说明」，同时附 GitHub 源码仓库；报告里放体验版二维码截图。
6. **本机没有微信开发者工具，怎么在开发过程中"看见"界面**：不能每次改完都靠想象，也没法截图。
   - 解决：写了一个只服务于本项目的预览渲染器（`preview/build.js` + `preview/web-runtime.js`）：在浏览器里 mock `wx`/`Page`/`getApp`，解析 WXML（`wx:for`、`wx:if`、`{{}}`、自定义组件）与 WXSS（`rpx`→`px`），把真实的页面代码打包成可直接双击打开的 HTML；再用 Edge 无头模式截图、Pillow 拼图。
   - 代价：不执行真机手势，所以只用于"看"，交互仍靠 `preview/flow-test.js` 在数据层跑通。
   - 收获：渲染器和截图本身也成了报告"开发历史"的证据；后来还基于它写了布局审计脚本（见第 8 条）。
7. **积分抵扣规则改了三版**：从 20% → 10% + 保证金 → 店家最终确认 5% + 会员 96 折；每次改动都要同步结算页、商品详情、积分页文案和测试断言，其中一次改完还有文案残留（结算页仍写"跳到店长收款码"、订单页仍写"冻结的 200 积分"）。
   - 解决：把抵扣公式收敛到 `store.createOrder` 一处，结算页只读 `maxUse`；`preview/flow-test.js` 扩到 54 条断言锁住金额、积分、会员折扣、退货结算；改完规则后全项目搜"保证金 / 冻结 / 收款码"做文案清理。
8. **"UI 有点怪怪的"却说不清哪里怪**：用户反馈很真实但不具体，而开发机上又看不了截图（当前模型不支持读图）。
   - 解决：把"怪"拆成可测的量——写 `preview/make-audit.js`，注入审计脚本测：横向溢出、文字被行高裁切、滚动到底时最后一格被固定底栏盖住；用 `preview/contrast.js` 算每个灰阶在奶油底上的对比度；用 `preview/bump-fonts.js` 把所有 `font-size` 按单调映射整体上调。
   - 结果：审计出 `cart-bar`/`bar` 横向溢出到 `-187..563`（`position:fixed` 在宽视口按视口定位）、`#9a9184` 只有 2.81:1 对比度、大量 18–22rpx 说明文字实际只有 9–11px；修完后 14 条路由（含 `admin?demo=1`、`pay?id=latest`、`order?id=latest`）审计全部通过。
   - 收获：把主观反馈翻译成客观指标，是这次最有用的一条方法论。
9. **网页演示版详情页白屏**：新加 `utils/size.js` 后，`web/index.html#/detail?id=p1` 打开只有一行红字 `Uncaught Error: missing module utils/size`。
   - 原因：网页版不是打包工具，`preview/web-build.js` 里有一份 `moduleFiles` 白名单，只有列进去的模块才会被塞进产物；漏了新的工具模块，页面一 `require` 就炸。
   - 解决：把 `utils/size.js` 加进白名单并重建（244KB / 18 图）；顺手在交接卡里写下"以后新增 `utils/*.js` 必须同步白名单"。
   - 教训：自建渲染器的"隐式白名单"是最容易漏的一环，因为它只在运行时炸，构建本身不报错。
10. **尺码表单在窄屏被撑破**：第一版截图里体重输入框和单位「kg」被裁到屏幕外。
   - 原因：原生 `<input>` 在 flex 容器里默认 `min-width:auto`，按内容宽度撑开，两个输入框 + 按钮就超出了 375 宽。
   - 解决：给输入框和它的容器加 `min-width:0`、`width:100%`，按钮加 `flex:0 0 auto`；改完重新截图核对，输入框和单位都完整落在卡片里。
   - 收获：纯 CSS 的错只有截图能看出来，`flow-test` 永远全过——所以 UI 改动必须配一次真截图。
11. **云端比本地"松"了一档：`update` 是合并语义**：店长第一次在真云端点「发货」，云函数报 `-502001 Cannot create field 'company' in element {tracking: null}`。
    - 原因：云数据库的 `update` 对对象/数组是**合并**而不是替换——`tracking` 原本是 `null`，没法往里加子字段；`timeline` 数组按索引合并还会丢新增项。
    - 解决：在 `cloudfunctions/api/common/wxdb.js` 里统一对对象/数组值包一层 `db.command.set(v)`，标量照旧。修完实测发货 + 补单号都 ok，`timeline` 长度 4（提交/支付/发货/补单号）。
    - 教训：内存库自测（纯 JS 对象直接赋值）永远查不出这类"云端语义差异"，只有真调用才会撞。
12. **店长改价"本地成了、云端没动"**：店长台改完价自己手机显示新价，另一台手机还是老价。
    - 原因：客户端传的是 `{id, patch}` 嵌套对象，而云函数 `updateProduct` 读的是扁平字段（`payload.price/stock/...`），于是每次都返回「没有要改的字段」。
    - 解决：`api.js` 里摊平成 `Object.assign({}, patch, {id})`；表单传的是字符串，服务端再用 `Number()` 兜一层。顺带发现下架开关的 `onSale` 服务端根本没写，一并补上，商品列表也改成以云端 `products` 为准。
    - 教训：「响应成功」不等于「数据写进去了」，改完必须回读一次云端。
13. **开发工具缓存让"云端没生效"的假象持续了半小时**：明明把库存改成 3、也重新部署了云函数，模拟器页面一直显示 86。
    - 原因：开发者工具缓存编译产物，只 `close/open` 项目仍跑旧 bundle。
    - 解决：`cli.bat cache --clean all` → `close` → `open` 才彻底刷新。
    - 教训：排查"云端没生效"之前，先证明本机跑的是最新代码——在页面里塞一个 `dbg` 字段，比猜快得多。
